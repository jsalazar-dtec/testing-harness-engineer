# POST /users: registro con validacion y sin filtrar credenciales

Los clientes de esta API necesitan crear cuentas de usuario. Hoy no existe el
endpoint de registro. Se agrega POST /users con validacion de entrada,
deteccion de email duplicado, y almacenamiento en memoria (in-memory Map) —
la persistencia contra una BD real queda fuera de este Issue.

## Reglas de negocio

- El email es unico en todo el sistema. Un segundo intento con el mismo
  email devuelve 409, y el primer usuario queda tal cual.
- El password se guarda hasheado con bcrypt (cost >= 10). En claro no se
  guarda en ningun sitio, ni en logs.
- El password de entrada tiene que cumplir: al menos 12 caracteres, al menos
  una mayuscula, una minuscula, un digito y un caracter no alfanumerico.
  Un password que no cumple devuelve 400 con el error `password_debil`.
- La respuesta 201 devuelve id (uuid v4) y email. Nunca `password`,
  `passwordHash` ni ningun otro campo interno.
- El id del usuario NO es autoincremental — se genera con uuid.

## Resultado esperado

- POST /users con payload valido devuelve 201 con `{ id: <uuid v4>, email }`.
- El campo `password` (o `passwordHash`) nunca aparece en la respuesta.
- POST /users con un email ya registrado devuelve 409 y `{ error: "email_ya_registrado" }`.
- POST /users con password de menos de 12 caracteres devuelve 400 y `{ error: "password_debil" }`.
- POST /users con password sin mayuscula/minuscula/digito/simbolo devuelve 400.
- POST /users sin email o con email invalido devuelve 400 y `{ error: "email_invalido" }`.
- El usuario queda persistido en el storage en memoria con el password hasheado (no en claro).
- La cobertura de tests del modulo users >= 95%.

## Herramientas

NestJS 11, TypeScript, jest, class-validator para DTOs, bcryptjs para el hash,
uuid v4 para el id. Storage en memoria (Map dentro del provider) — sin
TypeORM, sin BD real todavia.
